# Blackharbor (preview repo)

A superhero campaign game modelled on Kingdom Death: Monster. Vanilla JS, no build step: GitHub Pages serves the files as they are.

## Working rules
- This repo is the **preview**. Push changes here (PR into `main`); copy to the live repo `drag0nblad3/Blackharbor` only with Tyler's OK.
- Read as little as possible: find code with `node tools/q.js where <word>` or `outline <regex>` (prints file:line), then read only that file or range. Ask about data with `q.js gear|villain|sets|...`. Use `tools/sim.js` for balance (under 1,000 fights total). See `tools/README.md`.
- Saves: key in `src/core/save.js` (`blackharbor-v4`, Pages adds `-preview`). Keep every migration; add one when the save shape changes.
- Data tables in `src/data/` stay plain literals (no functions) and hold final values: edit in place, never add patch blocks.
- Before pushing a game change run the fast tests from `.github/workflows/preview-gate.yml` that touch it; CI runs them all.

## How the code fits together
- `index.html` loads every `src/**` script in order as classic scripts, so all top-level names are shared globals. Code that runs while the page loads (outside a function) may only use names from files listed **earlier**. Everything else is called at runtime and can live anywhere.
- One global state object `S` (saved by `save()`); `render()` redraws the whole `#app` from it.
- **Screens:** `bodyMain()` in `src/ui/render.js` picks the view from `S.phase`/`S.view`. A new screen = a view function in its own file + one line there.
- **Buttons:** `data-a="name:p1:p2:p3"` runs `ACT.name(p1,p2,p3,name,el,event)`, then `render()` (return `NO_RENDER` to skip). Register handlers at the bottom of the file that owns the feature (`ACT.build=...`); `src/ui/input.js` only dispatches.
- Board taps go to `onCell` (`src/battle/hero-move.js`).

## Styles (`css/`)
Stylesheets load in this order, and later files win ties, so keep a rule in the layer it overrides from:
`base` (in the head: page frame, fonts, buttons, panels, cards, shared art) · `battle-board` hexes, tokens, lairs, terrain · `battle-fx` splash pages, attack/page animations · `battle` fight layout · `campaign` creation, Arc/event screens · `hq` · `overlays` menus, tips, tutorial, playbook (these six hold the old game.css/art.css rules by screen) · then the later layers as they were: `investigation` · `comic-ui` (paper skin over HQ/roster/villains/fight) · `pulp-details` · `villain-portraits` · `battle-art` (illustrated board pack; the combat lab toggles it) · `equipment-icons` · `villain-covers` · `hero-loadout` · `mobile` (phone condense, last).
To restyle a screen, grep its class across `css/` (`grep -n "bh-roster" css/*.css`): its base rules sit in the screen file, and comic-ui/pulp-details may override them.

## Where planned features go
- Start page, story scenes: new view files (e.g. `src/ui/start.js`, `src/campaign/story.js`) + a line in `bodyMain`; story text as data in `src/data/`.
- Extra campaigns with the same heroes and bases: campaign data in `src/data/`, flow in `src/campaign/`.
- Sound and music: a new `src/audio/` loaded after `src/core/`, called from fight events (`fx`, `log`, splashes) and `ACT` handlers.
- Sprite battle graphics: `src/art/` plus `src/battle/view.js` (board drawing) and `src/battle/anim.js`; styles in `css/battle-board.css`, or a new art pack beside `css/battle-art.css`.
